~~~~text
## 一、比赛到底要求我们做什么

官方不是让我们单纯拿一个“电力巡检机器人”去比赛，而是要求围绕四个问题做专项升级：

1. BDS 短时中断 + LiDAR 几何退化同时发生时，仍然连续高精度定位；
2. 动态目标和异常反射情况下，稳定提取 LiDAR 特征；
3. 剧烈运动、场景切换、感知退化情况下，进行具身主动重定位；
4. 做出实体无人平台，并集成北斗短报文通信。fileciteturn62file0L11-L25

而且最终不是“功能能跑就行”，官方给了三个非常硬的数字：

| 指标 | 官方要求 |
|---|---:|
| BDS 中断 + LiDAR 退化时定位误差 | 平面、高程均优于 **20 cm** |
| 动态目标剔除后的有效特征重复率 | ≥ **95%** |
| 退化环境重定位成功率 | > **95%** |
| 北斗短报文 | 完成实体样机集成与验证 |

fileciteturn41file1L64-L72

所以我们的目标不能是“把几个功能写出来”，而应该是：

**功能 → 实机运行 → 可重复实验 → 数据 → 指标 → 报告证据。**

# 三、最主要的缺口是什么

现在真正影响比赛结果的，不是 Web 页面、小程序或者再加几个 AI 功能。

优先级应该变成：

**P0：比赛三个量化指标 + 北斗短报文。**

尤其是第一项很危险：

### BDS + LiDAR 并发退化

现有机器人虽然有：

`Wheel Odom + IMU + LiDAR/AMCL + GNSS数据`

但还没有形成：

`BDS质量检测 → 异常识别 → LiDAR退化检测 → 自适应权重/模式切换 → 多源连续定位 → BDS恢复重接入`

这才是比赛真正要求的东西。

### 动态 LiDAR 特征

不能只说“Nav2 能避障”。

比赛问的是：

**动态目标剔除以后，相邻帧有效特征重复率 ≥95%。**

这意味着我们要有一套明确的：

`点云/扫描 → 动态/异常点识别 → 剔除 → 稳定特征提取 → 跨帧匹配 → repeat rate计算`

而且必须有计算脚本和实验数据。

### 主动重定位

已有：

`AMCL swing`  
`Scan-map matching`

下一步不是推倒重来，而是把它们组合起来：

`定位质量下降检测`
→ `判断是否需要主动动作`
→ `选择动作`
→ `旋转/移动主动获取信息`
→ `Scan-map候选生成`
→ `AMCL重初始化`
→ `恢复确认`

这样才更接近官方说的“感知—运动—决策—环境交互”的具身主动重定位。官方本身强调的也是这种感知、动作、决策一体化。fileciteturn62file9L297-L323

```text

# 六、M2｜8月29日—9月2日：退化感知 + LiDAR 特征

这一阶段同时解决比赛前两个技术难点的一部分。

需要建立：

### LiDAR 几何退化判断

例如根据：

- 有效测距点比例；
- 空间分布；
- 几何约束方向；
- 特征可观性；
- 匹配残差；

判断 LiDAR 当前是：

`正常 / 弱退化 / 强退化`

### 动态目标与异常反射处理

形成比赛专用 LiDAR 前端：

```text
LaserScan / PointCloud
        ↓
预处理
        ↓
异常反射/离群点处理
        ↓
动态目标识别
        ↓
动态点剔除
        ↓
稳定特征提取
        ↓
相邻帧特征匹配
        ↓
Repeat Rate
```

最后必须有：

```text
feature_repeat_benchmark
```

能自动输出：

`有效特征数 / 匹配数 / 重复率`

**Gate M2：能用脚本直接计算官方第二项指标。**

# 七、M3｜9月2日—9月5日：具身主动重定位

利用现有代码，不重造轮子。

已有基础：

```text
AMCL global relocalization
+
旋转扫描
+
Scan-to-Map matching
```

升级为：

```text
定位置信度监测
        ↓
退化/发散判断
        ↓
主动重定位决策
        ↓
选择观测动作
        ↓
旋转/小范围运动
        ↓
重新采集LiDAR
        ↓
Scan-to-Map候选
        ↓
AMCL恢复
        ↓
恢复质量验证
```

然后做统一测试程序。

例如一次实验自动记录：

```text
scenario
initial_error
trigger_time
recovery_time
final_pose_error
success/fail
```

最后自动计算：

**Success Rate = 成功次数 / 总测试次数**

目标不是写一句“成功率高”，而是最后能拿出：

> 例如 N 次独立退化实验，成功 X 次，成功率 Y%。

**Gate M3：正式统计值 >95% 才能在方案文档里写 >95%。**

# 八、M4｜9月5日—9月8日：北斗短报文

这是目前最大的硬件风险之一。

**WTRTK980 RTK/GNSS ≠ 已证明具备北斗短报文能力。**

所以 M0 必须最先确认。

如果没有短报文硬件：

> **马上采购/借用/联系实验室。**

不要拖到 9 月 10 日再发现没有设备。

最终至少形成：

```text
ROS2 / Driver
      ↓
短报文发送
      ↓
北斗链路
      ↓
接收
      ↓
消息状态
      ↓
日志记录
```

实验材料：

- 硬件照片；
- 接线；
- 驱动；
- ROS2 Topic/Service；
- TX/RX 日志；
- 成功发送记录；
- 接收记录；
~~~~
